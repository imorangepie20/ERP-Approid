2026-10-04. 실제 Spring DB 수납과 읽기 화면을 연결한다. FIN-01 전체 완료나 회계 전표 구현을 뜻하지 않는다.

## API와 잔액

- 목록/요약 계약은 [미수 목록](receivables-list.md)을 따른다. 원금 `amount`와 수납기일은 수납으로 변경하지 않는다.
- `collectedAmount`는 이월을 포함한 총 수납액, `openingCollectedAmount`는 기존 완료 상태에서 이월한 금액,
  `remainingAmount = amount - collectedAmount`다. 잔액은 음수가 될 수 없다.
- `GET /api/core/receivables/{id}?page=0&size=20`은 현재 미수와 `collections` Spring Page를 한
  REPEATABLE_READ 스냅샷으로 반환한다. 이력은 ID 내림차순이며 page=0..10000, size=1..100이다.
- 읽기 권한은 ADMIN/SALES/ACCOUNTING, 수납 권한은 ADMIN/ACCOUNTING이다. 무인증 401, 다른 역할 403.
- `POST /api/core/receivables/{id}/collect`의 JSON 본문은 다음처럼 **필수**다.

```json
{"amount":30000,"collectedOn":"2026-10-04","requestId":"aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa"}
```

`amount`는 양수 정수 KRW이며 소수·숫자 문자열·0·음수는 400이다. 실제 날짜와 UUID가 필요하고,
수납일은 서버 Asia/Seoul 오늘 이후일 수 없다. 과거 수납일 입력은 허용하되 실제 기록 시각은 별도로 남긴다.
**이전 본문 없는 상태 변경 호출은 400으로 차단한다.** 응답 계약도 단일 미수에서 아래 결과로 변경된다.

200 응답은 `{receivable, collection, replayed}`다. `collection`은 ID, requestId, 금액, 수납일,
처리 후 잔액 스냅샷, 인증 사용자 actorId, Trace ID, 실제 기록 시각을 포함한다. 사용자 이름이나 과거 정황을 추정하지 않는다.
부분수납은 기존 저장 상태를 유지하고, 잔액을 전부 수납하면 `수납완료`로 전환한다. 연체 판단은 양수 잔액과 한국 날짜 기준이다.
원금 0인 기존/신규 미수 문서는 연체나 수납 대상으로 표시하지 않는다.

## 중복·동시성·감사

- 요청 키는 **미수 문서별** UUID다. 부모 미수의 비관적 쓰기 잠금 아래 잔액과 기존 키를 재확인한다.
- 같은 문서/키/금액/수납일/**인증 처리자**의 재전송은 원래 이력과 현재 미수를 반환하고 `replayed=true`다.
  이후 다른 수납이 있었다면 원래 이력의 잔액 스냅샷과 현재 미수 잔액은 다를 수 있다.
- 키를 다른 입력/처리자로 재사용하면 409 DUPLICATE. 이미 완료/잔액 없음은 409 INVALID_STATE_TRANSITION,
  잔액 초과는 422 BUSINESS_RULE_VIOLATION, 없는 문서는 404다. 오류는 공통 코드/Trace ID를 사용한다.
- DB `(receivable_id, request_id)` 고유키와 양수 이력/잔액 제약이 추가 방어선이다.
  동시에 서로 다른 키를 보내도 잠금 후 잔액을 다시 검증하므로 합계가 원금을 넘지 않는다.
- 총 수납액/상태, 새 이력, 민감 `COLLECT` 감사는 한 트랜잭션이다. 감사 저장 실패도 전체 롤백한다.
  성공 재전송은 새 이력이나 감사를 만들지 않는다. 수납 이력 변경·삭제 API는 없다.
- 향후 전표의 연결 지점은 안정적인 `collection.id`와 미수/인증 처리자/감사다.
  **실제 전표 생성, 은행 대사, 수납 취소·환불, 기간별 현금흐름 분석은 구현하지 않았다.**

## 화면과 통신 오류

`/sales/receivables`의 각 행에서 수납·이력을 연다. 실제 원금/총 수납/잔액과 서버 페이지 이력을 표시한다.
SALES는 조회만, ADMIN/ACCOUNTING은 금액·공통 달력 수납일 입력과 전액 입력을 제공한다.
검증된 성공 후 미수/영업 분석/대시보드 Query를 무효화한다. 분석의 기존 문서 원금을 수납액이나 현금흐름으로 바꾸지 않는다.

전송 **전** 사용자/문서별 `sessionStorage`에 요청 UUID와 금액·일자를 보관한다. JWT는 보관하지 않는다.
응답 유실, 500, 잘못된 성공 응답은 성공으로 표시하지 않고 입력/키를 고정해 명시적 재시도를 제공한다.
모달을 닫고 다시 열어도 같은 브라우저 세션의 미확인 요청을 재사용한다. 자동 mutation 재시도는 없다.
400/403/404/422의 확정 실패만 명시적으로 입력 재작성을 허용한다. 409는 키를 자동으로 버리지 않는다.
저장소 접근 실패/손상은 새 POST를 차단한다. 브라우저 세션 종료/저장소 삭제 이후까지 키 복구를 보장하지 않으므로
그 경우 먼저 실제 이력을 확인해야 한다. 여러 기기에서 새 UUID로 같은 외부 입금을 등록하는 업무 중복까지 판별하지는 않는다.

독촉 모달 TODO-003은 [검토 전용 모달](receivables-reminders.md)로 연결했다. 실제 발송 TODO-004/047은 미완료이며 발송 버튼은 비활성 상태다.

## 마이그레이션과 운영 경계

공유된 V1–V15를 수정하지 않고 다음을 순차 적용한다.

1. V16: 금액 컬럼과 빈 수납 이력 테이블/인덱스/고유키 추가.
2. V17: 기존 `수납완료` 문서는 원금 전액을 총 수납/이월 금액으로 보존, 나머지는 0.
   **가짜 이력·수납일·처리자를 생성하지 않는다.** 원금/기일은 유지하지만 기존 updated_at 트리거는 실행될 수 있다.
3. V18: 원금/이월/총 수납 범위와 완료 상태의 전액 일치 제약. 불일치한 기존 금액은 자동 보정하지 않고 실패시킨다.

배포 전 실제 데이터의 상태/금액 정합성과 백업을 확인하고 수납 쓰기를 중지한 상태로 호환 백엔드와 함께 적용한다.
큰 기존 테이블에서 V17 UPDATE와 V18 제약 검증의 잠금/실행 시간을 별도로 확인해야 한다.
이는 forward-only 금액/이력 변경이다. 장애 시 수납 쓰기를 중지하고 **새 계약·스키마와 호환되는** 앱으로 복구한다.
옛 상태 변경만 하는 백엔드는 새 제약과 호환되지 않으며, 롤백을 위해 수납 이력이나 금액 컬럼을 삭제해서는 안 된다.
이번 검증은 격리 Testcontainers의 V15 과거 행 업그레이드다. 운영 DB 복사본/운영 마이그레이션/배포는 수행하지 않았다.
