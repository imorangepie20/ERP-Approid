# Spring 운영 대시보드 계약

2026-10-04 사용자 결정으로 ANL-01/02는 기존 Spring에서 구현한다. 별도 FastAPI 서비스나 개발 환경을
추가하지 않는다. 확장 분석(`/analytics`, ANL-03)은 아직 프로토타입이다. MRP의 실제 Spring 계약은
[MRP 발주제안](analytics-mrp.md)에 기록한다.

## 조회 경계

`GET /api/core/analytics/dashboard`는 기존 JWT로 인증된 사용자에게 공용 운영 집계를 제공한다.
쓰기 엔드포인트는 없다. KPI·월별 추이·현재 위험 알림·제외 이력을 단일 응답과
`@Transactional(readOnly=true, isolation=REPEATABLE_READ)`에서 조회해 섹션 간 시점 불일치를 막는다.
기존 core 클라이언트를 쓰므로 `VITE_API_ANALYTICS_URL`의 별도 서버로 요청하지 않는다.

- `from`, `to`: 서울 날짜, 양 끝 포함. 기본값은 이번 달 1일~오늘. 최대 366일, 미래 종료일 금지.
- `itemId`: 생략하면 전체 품목. 양수인 존재하는 품목만 허용(잘못된 ID 400, 없는 품목 404).
- `asOf`: 서버의 조회 시작시각(UTC ISO instant), `timeZone=Asia/Seoul`. 완료/출하 날짜도 서울 기준이다.
- 수주잔고·위험 알림·날짜 미확인 건수는 **현재 스냅샷**이다. 과거 종료일의 재고/잔고를 복원한 값이 아니다.
- 일자별 자료를 조회기간으로 먼저 제한한 뒤 월별 집계한다. 누락 월은 0이며 최대 13행이다.
- 알림은 종류·문서번호 오름차순으로 최대 20행과 전체 건수·생략 여부를 반환한다.
- 빈 분모의 비율은 `null`(화면 ‘해당 없음’), 실제 0%와 구분한다. 계산 불가와 제외 근거를 숨기지 않는다.
- 잘못된 기간/날짜 형식은 공통 `INVALID_INPUT` 400 및 Trace ID, 미인증은 401.
  지원하지 않는 HTTP 메서드는 공통 `METHOD_NOT_ALLOWED` 405 및 Allow 헤더다.

## 계산식과 원천

| 지표 | 계산식·원천 | 기간 기준 |
| --- | --- | --- |
| 매출(원) | 출하완료/매출반영 상태이며 실제 `confirmed_date`, 수불·미수금 연결이 있는 출하의 정수 원 `amount` 합계. 송장/배송예정일을 실적일로 간주하지 않음 | 출하확정일 |
| 생산액(기준단가 환산·원) | 완료/마감 오더 중 동일 품목·WORK_ORDER 참조의 생산입고 수불이 있는 오더. 오더별 `floor(good_qty × 현재 items.price)` 합계. 중복 참조는 최초 생산입고일로 하나만 집계. **실제 제조원가가 아님**, 단가 변경 시 과거 환산액도 변함 | 최초 생산입고일 |
| 현재 수주잔고(원/건) | 확정/생산중 수주의 `max(amount − 연결된 확정 출하 amount 합계, 0)` 합계와 수주 건수. 대기·취소·출하완료 수주는 제외 | 조회 시점, 기간 미적용 |
| 납기준수율(%) | 기간 내 납기가 이미 지난 수주 중 납기일까지 전량 출하확정한 수주 건수 / 판정 가능한 수주 건수 × 100, 소수 2자리 HALF_UP. 오늘 납기는 아직 끝나지 않았으므로 제외. 대기·취소 제외 | 수주 납기일, 오늘 이전 |
| 완료 오더 평균 불량률(%) | 각 오더 `defect_qty/(good_qty+defect_qty)×100`의 단순 평균, 소수 2자리 반올림. 서로 다른 kg/EA 등 단위를 합산한 수량가중 불량률이 아님 | 최초 생산입고일 |
| 재고회전율 | 일반적으로 기간 매출원가 / 기간 평균 재고원가. 현재 DB에 원가 및 평균 재고원가 이력이 없어 **null + 이유** 반환. 판매/기준단가를 원가로 대체하지 않음 | 원가 이력 선행 필요 |
| 현재 위험 알림 | `stock < safety_stock` 품목, `due_date < 서울 오늘`인 지시/진행중 오더 및 확정/생산중 수주. 품목별 단위를 표시하며 위험 분류는 수량 부족/실제 납기 경과만 사용 | 조회 시점, 기간 미적용 |

완료 상태지만 출하확정일·수불·미수금 링크가 없는 과거 출하 및 생산입고 참조가 없는 과거 완료 오더는
기간에 배정하지 않고 전체 날짜 미확인 건수로 반환한다. 납기 대상에 과거 미연결 완료 출하가 있거나,
출하완료 수주의 확인된 출하수량이 주문수량보다 작은 경우 납기 판정 불명으로 분모·분자 모두에서 제외한다.
따라서 납기준수율은 **확인된 수주만**의 비율이며 전체 과거 수주 성과로 해석하면 안 된다.

## 검증 기준

`DashboardIntegrationTest`는 별도 PostgreSQL Testcontainer에서 품목별 실제 SQL 이력을 만든다.
부분출하 400원 + 전량출하 1,000원 → 매출 1,400원, 완료 양품 8EA+1EA × 100원 → 생산액 900원,
현재 잔고 600원+1,000원 → 1,600원, 납기준수 1/2 → 50%, 오더 불량률 20%와 50% 평균 → 35%를 비교한다.
중복 수불 참조, 미연결 과거 이력, 오늘 납기, 기간 밖 생산, 빈 분모, 366일 경계, 인증·405·OpenAPI,
알림 상한 및 업무 감사 로그 불변을 함께 검사한다.

프런트 API/화면 테스트는 오류·Trace ID·재시도·빈 값·서울 날짜 경계·조회 적용·실제 품목 ID·GET만 사용·
접근성·위험 링크·응답 정합성을 확인한다. 실제 Chromium 거래 흐름은 생산/출하 후 해당 품목의 매출
1,000원·생산액 1,000원·잔고 0원·완료 오더 1건을 API와 화면에서 비교하고 새로고침 후 다시 확인한다.

ANL-02는 Spring 다단계 BOM 전개·발주잔량 반영·검토 후 실제 발주 연결로 이어진다.
