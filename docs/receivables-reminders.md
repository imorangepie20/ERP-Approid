# 독촉 검토 모달 계약 (TODO-003)

2026-10-04. 실제 미수의 대상·수신자·내용을 **화면에서 검토**하는 단계다.
실제 발송·저장·발송 결과 이력은 TODO-004/047이며 이번에 구현하지 않았다.

## 읽기 API와 권한

- 대상은 기존 `GET /api/core/receivables?overdue=true`의 실제 날짜 연체 미수다.
  서버 리터럴 검색/기일 정렬/10개 페이지를 사용하고 한 번에 한 문서를 선택한다.
  상위 목록 필터의 대상 전체를 자동 선택하거나 대량 발송하지 않는다.
- 새 `GET /api/core/receivables/{id}/reminder-preview`는 `{receivable,contactName,contact}`를 반환한다.
  미수·총 수납·현재 잔액·한국 기준일 및 **현재** 거래처 연락처를 같은 REPEATABLE_READ 읽기 스냅샷으로 조회한다.
- ADMIN/SALES/ACCOUNTING은 검토 가능하다. 이는 기존 미수 읽기 권한이며 **향후 발송 권한을 확정하는 정책이 아니다.**
  무인증 401, 다른 역할 403, 양수가 아닌 ID 400, 없는 ID 404와 공통 오류/Trace ID다.
- 미등록 contactName/contact는 명시적 null이다. 고객명·수주명으로 주소를 추정하지 않는다.
  완료/비연체 문서도 사실 그대로 조회하지만 UI 검토 확인 대상은 양수 잔액의 날짜 연체 문서로 제한한다.
- preview POST는 없다(405). 수납 상태·기일·저장 연체일·수납 이력·감사 로그를 변경하지 않는다.
  DB 스키마 변경, 외부 메시지 클라이언트, 큐/발송 요청 엔드포인트도 추가하지 않았다.

## 화면과 확인

`/sales/receivables`의 ‘독촉 발송 검토’ 버튼은 실제 대상 선택 모달을 연다.
검색/페이지 이동 시 이전 선택과 입력을 버려 보이지 않는 문서를 확인하지 않는다.
미수/수신자 읽기 오류·빈 목록은 명시적으로 표시하고 Trace ID와 재시도를 제공한다. 요청 취소 신호를 전달한다.

기존 거래처의 `contact`는 구분 없는 연락처 문자열이다. 등록 연락처를 초기값으로만 제공하고,
사용자가 검토용 EMAIL/SMS 채널과 수신 주소/번호를 확인한다. EMAIL은 기본 선택이며 전화번호에서 채널을 추정하지 않는다.
이메일은 단일 주소 형식/최대 254자, SMS는 공백·하이픈을 제외한 국내 휴대전화 형식을 검사한다.
**이는 전송 가능성·주소 소유권·동의/차단 여부 검증이 아니다.** 공급사·국제 번호·정확한 발송 정책은 TODO-047에서 확정한다.

내용은 선택 미수의 고객명·청구번호·수납기일·현재 잔액·한국 조회 기준일로 생성한다.
부분수납의 원금을 미납 금액으로 표시하지 않는다. 추가 안내는 최대 1,000자이며 React 텍스트로 표시해 HTML을 실행하지 않는다.
제목/본문에는 확인되지 않은 입금 계좌, 발신자, 연체료나 법적 조치 문구를 만들지 않는다.
수신자·채널·추가 안내를 바꾸면 확인 체크를 해제한다.

‘수신 대상과 내용을 확인했습니다’ 체크 후 ‘미리보기 확인’을 누르면 최신 preview를 다시 조회한다.
잔액/상태/기일/기준일/고객·연락처 등 응답이 달라지면 기존 입력·체크를 재설정하고 변경 안내를 표시한다.
수납완료·잔액 0·비연체로 바뀌면 확인을 차단한다. 조회 실패도 검토 완료로 바꾸지 않는다.
동일한 최신 값일 때만 **‘검토 완료 · 미발송’**으로 표시한다. 이 상태는 해당 조회 시점의 화면 검토 결과일 뿐,
후속 수정이나 실제 발송 시점까지 잔액·주소를 예약하거나 보장하지 않는다. TODO-004 발송 서버는 다시 검증해야 한다.

실제 ‘발송 (준비 중)’ 버튼은 항상 비활성이다. POST·메일 링크·외부 발송·DataContext/브라우저 저장소·서버 초안 저장을 하지 않는다.
‘취소 / 닫기’(Escape 포함)는 입력을 폐기한다. 다시 열면 실제 정보를 새로 읽는다.
입력 수정은 확인 상태로부터 돌아갈 수 있으며 발송 성공 토스트나 가짜 발송 이력을 만들지 않는다.
