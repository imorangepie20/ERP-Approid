# Spring MRP 발주제안 계약

2026-10-04 사용자 결정에 따라 기존 Spring/JWT/core 클라이언트를 재사용한다.
추가 서버·DB·마이그레이션·통계 예측 모델을 만들지 않는다. `/purchase/mrp`는 DataContext가 아닌
실제 DB 조회이며 조회 자체는 재고·발주·감사를 변경하지 않는다.

## 입력과 조회 경계

`GET /api/core/analytics/mrp/suggestions`는 인증 사용자 모두에게 읽기 전용이며
`REPEATABLE_READ` 한 트랜잭션에서 품목/BOM/활성 작업/미입고 발주를 조회한다.

- `through`: 서울 오늘~365일 후 포함. 기본 오늘+90일. 활성 작업은 지시/진행중 중 착수일이 종료일 이하인 건이다.
  연체 작업도 포함하고 취소/완료/마감 및 종료일 이후 착수 작업은 제외한다.
- `itemId`: 양수의 존재하는 품목. 전체 계획을 계산한 **후** 표시 필터를 적용하므로 공유 자재를 과소계산하지 않는다.
- `page`: 0~100000, `size`: 1~100(기본 50). 소요일·품번 순이며 범위 밖 페이지는 빈 배열이다.
- `asOf`: UTC 조회 시작시각, `timeZone=Asia/Seoul`. 요약 건수는 전체 계획 기준이고 행/전체 페이지는 표시 필터 기준이다.
- 품목 10000, BOM 50000, 활성 작업/미입고 발주 각각 10000 한도. 초과하면 422로 실패하며 일부만 계산하지 않는다.
- 순환 BOM은 전체 조회 409 `BOM_CYCLE`. 없는 BOM은 해당 행 `MISSING_BOM`으로 명시한다.
  잘못된 기간/페이지는 400, 없는 품목 404, 미인증 401. 공통 오류/Trace ID를 유지한다.

## 수량·기간 정책

1. BOM 수량은 부모 기본단위 1당 자품목 기본단위 계수다. 손실률은 수율의 역수가 아니라 **추가 소요율**이다.
   `부모량 × BOM qty × (1 + lossRate/100)`, 각 단계 소수 4자리 올림. 손실 100%는 두 배다.
2. 구성품 불출/소비 이력이 아직 없다. 활성 작업 전체 지시수량을 보수적인 구성품 소요로 전개한다.
   누적 양품을 구성품 불출량으로 추정하지 않고, 완료 작업의 과거 미불출 소비도 복원하지 않는다.
   따라서 현재고 정합성이 실제 소비와 다를 수 있으며 **계획 참고값**이지 실소비 원장/재고 예약이 아니다.
3. 부모부터 위상 순서로 공유 자품목 소요를 합산하고 품목별 공급을 한 번만 차감한다.
   `부족 = max(소요 + 기존 안전재고 − 가용재고 − 미입고 발주 − 예정 생산, 0)`.
   부족한 제품/반제품만 추가 생산량으로 BOM을 전개한다. 이미 지시된 생산의 구성품은 해당 작업에서 전개한다.
4. 가용재고는 `max(items.stock − 비정상 또는 만료 Lot 잔량 합계, 0)`다.
   안전재고를 자동으로 바꾸지 않는다. 단위 변환·kg/EA 합산은 하지 않으며 모든 수량에 품목 단위를 붙인다.
5. 미입고 발주 = 발주/부분입고의 `max(qty − received_qty, 0)` 합계. 취소/입고완료는 제외한다.
   예정 생산 = 활성 작업 `max(qty − defect_qty, 0)`. 이는 확정 실적이 아닌 예정 양품이다.
6. 납기가 소요일보다 늦은 발주/생산도 수량에 차감한다. 계획 종료 이후 납기인 기존 발주도 차감해
   단순 지연을 이유로 중복 구매하지 않는다. 늦은 공급량을 따로 표시하고 적시 부족이면 `EXPEDITE`를 표시한다.
   시간구간별 ATP/확정 납기 약속 모델은 아니다.
7. 소요일은 실제 작업 착수일의 최솟값, 추가 생산의 구성품은 부모 소요일−부모 리드타임이다.
   안전재고만의 보충은 계획 종료일을 사용한다. 발주마감 = 소요일−품목 리드타임, 오늘 이전이면 경과 표시한다.
8. 자재 부족은 `PURCHASE`, BOM 있는 제품/반제품 부족은 `PRODUCE`, BOM 없음은 `MISSING_BOM`이다.
   추가 생산 오더·대체품·MOQ/EOQ·공급처는 자동 생성/선택하지 않는다.

## 검토 후 발주 전환

ADMIN/MATERIAL만 버튼을 사용하며 SALES 등은 조회한다. 서버도 기존 발주 POST에서 같은 권한을 검사한다.
선택한 행의 서버 제안량/품목 ID를 사용하고 발주처 기본값은 비워 둔다. 사용자가 실제 `발주처`를 선택하고
단가·배송예정일을 확인하면 기존 `POST /api/core/purchase-orders`에 저장한다.
품목 기준단가는 참고 기본값이며 공급 계약단가가 아니다. 기본 예정일은 소요일과 오늘+품목 리드타임 중 늦은 날이다.

발주번호 32자, 양수 수량 소수 4자리/정수 14자리, 양수 정수원 단가·합계는 JS 안전 정수 범위 이하다.
원 미만은 버린다. 고객사/외주처를 발주처로 쓰지 못한다. 트랜잭션 감사(actor/trace/before-after)를 재사용하며
발주 생성은 현재고를 늘리지 않는다. 같은 발주번호 중복은 409, mutation 자동 재시도 및 중복 submit은 없다.
저장 후 MRP/발주/대시보드를 재조회하고 실제 저장 문서를 표시하며 실제 발주 선택이 가능한 입고 화면으로 연결한다.

제안은 예약이 아니므로 확정 전 재조회해야 한다. 다른 사용자의 동시 발주를 막는 계획 예약/idempotency/bulk 승인,
발주 CRUD 화면 전체 전환은 후속 범위다. 실입고 이후에만 입고 업무가 재고를 변경한다.

## 재현 가능한 검증값

제품 10EA → 반제품 2EA(손실10%) 및 자재 1kg, 반제품 → 자재 3kg(손실5%).
반제품 현재고5/안전2/발주3/예정 양품3이면 반제품 추가 생산은 13EA다.
별도 반제품 작업4EA의 자재12.6kg + 추가 반제품13EA의 자재40.95kg + 제품 직접자재10kg = **63.55kg**.
자재 현재고10(보류1/만료1 제외 가용8), 안전2, 부분입고 발주잔량6이면 **발주 제안51.55kg**이다.
이를 단가100원으로 실제 저장하면 **5155원**, 현재고10 유지, 재조회 제안0 및 지연 공급 경고다.

`MrpCalculatorTest`/`MrpIntegrationTest`, 프런트 API/화면 테스트가 공유 합산·반올림·순환·기간·권한·감사·
잘못된 금액/단위·실제 발주/빈 결과/오류/달력/접근성을 검사한다. 실제 Chromium에서는 BOM 2EA×작업10EA×1.1
= 22EA를 2200원 발주로 전환하고 DB/재조회/새로고침에서도 확인한다. 개발 DB에는 테스트 거래를 넣지 않는다.
