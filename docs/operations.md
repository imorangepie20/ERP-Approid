# ERP-Approid 운영 정책

이 문서는 운영 데이터 보호, 스키마 변경, 로그 보존, 관리자 접근의 최소 정책과 실행 절차를 정의한다. 실제 운영 인프라의 스케줄러, 원격 저장소, 비밀 관리 시스템, 로그 수집기는 배포 환경에서 별도로 연결해야 한다.

## 운영 기동 계약

루트 `docker-compose.yml`과 `.env.example`은 로컬 개발 전용이다. 실제 운영은
`SPRING_PROFILES_ACTIVE=prod`를 명시하고 다음 값을 운영 비밀·설정 저장소에서 주입한다.

- `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USERNAME`, `DB_PASSWORD`: DB 비밀번호는 16 UTF-8 byte 이상
- `JWT_SECRET`: 공개 예제 문자열이 아닌 32 UTF-8 byte 이상의 값
- `INTERNAL_KEY`: JWT와 다른 32 UTF-8 byte 이상의 값
- `CORS_ALLOWED_ORIGINS`: 쉼표로 구분한 정확한 브라우저 origin 목록. wildcard 금지

활성 프로필의 기본값은 없다. 운영 프로필은 누락되거나 약한 secret, 개발·예제값, 동일한 JWT와
internal key, 비어 있거나 wildcard인 CORS 설정을 감지하면 기동을 중단한다. 운영에서는
Swagger UI와 OpenAPI JSON이 모두 비활성화되며 외부 설정으로 다시 켜거나 요청 본문 상한을
1MiB보다 크게 설정하면 기동을 중단한다. 활성 ADMIN에 개발용 `admin123` 비밀번호가 남아 있어도
웹 서비스 준비 전에 기동을 중단한다. 배포 전 다음을 별도 환경에서 확인한다.

1. 안전하지 않은 설정으로 기동이 실패한다.
2. 허용 origin의 preflight만 성공하고 credentials 헤더는 반환하지 않는다.
3. `/v3/api-docs`와 `/swagger-ui.html`이 노출되지 않는다.
4. TLS 종료 프록시가 `X-Forwarded-Proto`를 신뢰 경계 안에서 설정하고 HSTS가 반환된다.
5. 1MiB를 초과한 요청 본문은 trace ID가 포함된 `413 PAYLOAD_TOO_LARGE`로 거절된다.

## 데이터베이스 백업과 복구

### 목표와 주기

- 복구 시점 목표(RPO)는 **24시간 이내**다.
- PostgreSQL 논리 백업은 **매일 1회 이상** 실행한다.
- 복구 훈련은 **분기 1회 이상**, 그리고 PostgreSQL 메이저 버전 변경이나 백업 방식 변경 후에 실행한다.
- 백업 성공 여부, 파일 크기, SHA-256, 원격 저장소 업로드 결과를 운영 기록에 남긴다.
- 로컬 `backups/`는 임시 착륙 지점일 뿐 보존 저장소가 아니다. 생성된 `.dump`와 `.sha256`을 암호화된 별도 저장소로 전송하고 접근을 운영 담당자로 제한한다.
- 보존 기간과 세대 수는 개인정보·회계 데이터의 법적 요구사항을 확인한 뒤 운영 환경에서 확정한다. 만료된 백업은 승인된 절차로 폐기한다.

### 백업 실행

Compose의 `postgres` 서비스가 정상일 때 저장소 루트에서 실행한다.

```powershell
.\scripts\backup-postgres.ps1
```

기본 출력은 `backups/<database>-<timestamp>.dump`와 같은 이름의 `.sha256` 파일이다. 백업은 PostgreSQL custom format(`pg_dump --format=custom`)이며 owner와 privilege를 포함하지 않는다. PowerShell의 텍스트 리디렉션을 통하지 않으므로 바이너리 손상을 피한다.

운영 백업 디렉터리를 지정할 수 있다.

```powershell
.\scripts\backup-postgres.ps1 -OutputDirectory D:\erp-backups
```

### 안전한 복원

기본 복원은 원본과 다른 새 데이터베이스 이름을 자동 생성한다.

```powershell
.\scripts\restore-postgres.ps1 -BackupFile .\backups\erp_approid-20261001-120000.dump
```

스크립트는 기본적으로 `<dump>.sha256`을 검증한다. 체크섬 파일이 없거나 값이 다르면 복원을 중단한다. 기존 대상 데이터베이스는 `-ReplaceTargetDatabase` 없이는 삭제하지 않는다. 원본 `POSTGRES_DB`와 같은 이름으로 복원하려면 승인된 장애 복구 상황에서만 아래 두 옵션을 함께 사용해야 한다.

```powershell
.\scripts\restore-postgres.ps1 `
  -BackupFile D:\erp-backups\erp_approid-20261001-120000.dump `
  -TargetDatabase erp_approid `
  -ReplaceTargetDatabase `
  -AllowSourceDatabaseOverwrite
```

이 작업은 현재 원본 데이터베이스를 삭제한다. 실행 전에 `docker compose stop backend-spring`으로
애플리케이션 쓰기와 재연결을 중지하고, 대상과 백업 파일을 다시 확인하고, 변경 승인을 기록해야 한다.
스크립트도 애플리케이션 서비스가 실행 중이면 원본 복원을 거부하며, `pg_restore`는 단일 트랜잭션으로
실행된다. 체크섬 우회 옵션은 별도의 위험 승인과 파일 출처 검증 없이는 사용하지 않는다.

### 복구 훈련

```powershell
.\scripts\test-postgres-recovery.ps1
```

훈련 스크립트는 다음 절차를 자동화한다.

1. 현재 데이터베이스를 custom-format으로 임시 백업하고 SHA-256을 생성한다.
2. 고유한 임시 데이터베이스를 생성해 백업을 복원한다.
3. Flyway V8 성공 이력, 핵심 9개 테이블 접근, 역할·사용자 필수 행을 검증한다.
4. 성공과 실패 모두 `finally`에서 임시 데이터베이스와 로컬 임시 파일을 제거한다.

운영자는 실행 일시, 담당자, 백업 식별자, 소요 시간, 검증 결과, 실패 시 조치를 기록한다. `-DryRun`으로 실행 계획과 안전 게이트를 확인할 수 있지만 실제 복구 훈련을 대체하지 않는다.

## 데이터베이스 마이그레이션 정책

- 이미 공유된 Flyway migration은 수정하거나 삭제하지 않는 **append-only** 정책을 적용한다.
- 배포 전 데이터베이스 백업과 체크섬 검증을 완료한다.
- 배포 전후 `flyway_schema_history`의 버전과 성공 상태를 확인한다.
- 실패한 스키마 변경은 기존 migration을 편집하는 대신 새 migration으로 **forward-fix**하는 것을 원칙으로 한다.
- forward-fix가 불가능하고 데이터 무결성이 훼손된 경우 쓰기를 중지한 뒤 검증된 백업을 새 데이터베이스에 복원하고, 검증 후 연결 대상을 전환한다.
- 대용량 테이블 변경은 잠금 시간, 디스크 여유, 롤링 배포 호환성을 사전 검증한다.

## 로그 보존 경계

- Compose의 컨테이너별 로컬 로그(`10MB × 3개`)는 장애 직후 확인을 위한 순환 버퍼일 뿐이며, 보존 기간을 보장하는 장기·감사 저장소가 아니다.
- 애플리케이션 로그에는 trace ID와 인증된 사용자 식별자를 유지하되 비밀번호, JWT, 내부 키, 개인정보 전문을 남기지 않는다.
- 운영 환경은 JSON 로그를 외부 중앙 수집기로 전송하고, 전송 실패 경보와 접근 통제를 적용한다.
- 보안·감사 로그의 구체적인 보존 기간과 삭제 정책은 개인정보 및 회계 규정 검토 후 확정한다. 확정 전 자동 삭제 기능을 도입하지 않는다.
- 데이터베이스 백업과 로그는 장애 범위가 겹치지 않는 별도 저장소에 둔다.

## 관리자 접근과 비밀 회전

- 기본 `admin/admin123` 계정은 로컬 개발 전용이다. 운영 투입 전에 고유 관리자 계정을 만들고 기본 계정을 비활성화하거나 자격 증명을 교체한다.
- 공유 관리자 계정을 금지하고 관리자별 고유 계정과 최소 권한을 사용한다. 일상 업무 계정과 관리자 계정을 분리한다.
- 관리자 생성, 권한 변경, 비활성화는 승인자와 작업자를 분리하고 감사 로그로 추적한다.
- 퇴사·직무 변경 시 즉시 권한을 회수한다. 관리자 접근 권한은 분기마다 재검토한다.
- DB 비밀번호, JWT secret, internal key는 운영 비밀 관리 시스템에서 주입한다. 저장소, 이미지, 로그, 백업 스크립트 인자에 값을 기록하지 않는다.
- 서비스 비밀은 최소 분기 1회 회전을 기본으로 하고 긴급 회전 절차를 둔다. 노출 의심, 담당자 변경, 외부 서비스 침해 시에는 일정과 무관하게 즉시 회전하며 JWT secret과 internal key는 서로 다른 값으로 유지한다.
- 회전은 새 값 배포, 의존 서비스 확인, 기존 값 폐기, 감사 기록 순으로 수행한다. JWT 회전은 기존 토큰 만료와 강제 재인증 영향을 포함해 계획한다.

## 운영 점검 기록

매일 백업 작업은 최소한 다음 정보를 남긴다.

- 실행 시각과 실행 환경
- 데이터베이스 식별자와 백업 파일 식별자
- 파일 크기와 SHA-256
- 원격 저장소 전송 및 보존 정책 적용 결과
- 실패 여부, 재시도, 담당자 조치

분기 복구 훈련은 RPO 충족 여부와 함께 실제 복원 시간도 기록해 향후 복구 시간 목표(RTO)를 수립하는 근거로 사용한다.
